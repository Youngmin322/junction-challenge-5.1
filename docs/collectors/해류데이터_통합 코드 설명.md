# `해류데이터_통합.py` 설명

전국 해역의 해류 관측을 두 오픈API에서 받아 하나의 JSON으로 합치는 스크립트. **24시간에 1회 실행**을 전제로 한다.

---

## 무엇을 하는가

| 입력 | 내용 |
|---|---|
| `twRecent` 해양관측부이 38개소 | 점 관측, 관측소 고유 해상도(1~10분), 해류 + 수온·염분·바람·파랑 |
| `hfCurrent` 해수유동 HF-RADAR 13개소 | 격자 관측(98~737점), 1시간 간격, 해류만 |

두 자료를 **24개 정시 슬롯**에 맞춰 하나의 스키마로 병합한 뒤 JSON으로 내보낸다. CSV는 만들지 않는다.

---

## 왜 병합이 까다로운가

두 데이터는 축이 서로 **전치(transpose)** 되어 있다.

```
부이   : 좌표   1개 × 시각 1,384개    (시간은 촘촘, 공간 없음)
레이더 : 좌표 467개 × 시각     1개    (공간은 촘촘, 시간 없음)
```

그대로는 겹치는 지점이 없다. 그래서 **정시(每 시각 00분)를 공통 기준**으로 삼아 양쪽을 같은 슬롯에 스냅한다.

## 실행

```bash
python3 해류데이터_통합.py                     # 최근 24시간
python3 해류데이터_통합.py --date 20260821     # 특정 날짜 하루치
python3 해류데이터_통합.py -o dataset.json --compact
python3 해류데이터_통합.py --format geojson    # 지도용
python3 해류데이터_통합.py --no-series         # 용량 줄이기
```

하루 1회 자동 실행 (crontab, 매일 03:10):

```
10 3 * * * cd /경로 && /usr/bin/python3 해류데이터_통합.py -o /경로/dataset.json -q
```

서버 전송:

```python
from 해류데이터_통합 import build_dataset
requests.post(url, json=build_dataset())
```

## 출력 구조

```json
{
  "meta":             { 생성시각, 슬롯 목록, 건수, 해역별 집계, bbox, 경고 },
  "stations":         [ 관측소별 상태 (정상/오류/데이터없음, 최신시각) ],
  "cross_validation": [ 부이와 레이더가 겹치는 지점의 관측값 비교 ],
  "observations":     [ 24개 슬롯에 맞춘 통합 유속장 ],
  "buoy_series":      [ 부이 원해상도 시계열 ]
}
```

관측 1건의 형태 (부이·레이더 동일):

```json
{
  "src": "buoy",  "code": "HB_0009",  "name": "한수원_나곡",
  "region": "동해",  "lat": 37.11916,  "lon": 129.39583,
  "ts": "2026-08-22T21:00:00+09:00",
  "slot": "2026-08-22T21:00:00+09:00",
  "age_min": 0.0,
  "dir_deg": 297.0,  "speed_cms": 3.9,
  "u_ms": -0.03476,  "v_ms": 0.01771,
  "extra": { "wtem": 26.17 }
}
```

- `u_ms` / `v_ms` — 유향·유속을 동/북 성분(m/s)으로 미리 변환한 값. 이류 계산에 바로 쓴다
- `age_min` — 슬롯 시각과 실제 관측 시각의 차이(분). 0이면 정확히 일치
- `extra` — 부이만 갖는 수온·염분·바람·파랑. 레이더에는 없다

## 코드 흐름

```
probe_base_hour()      레이더 몇 곳을 찔러 실제 발행된 최신 정시를 찾는다
      ↓
fetch_buoy()  ×38      하루치를 원해상도로 받는다 (페이지네이션)
fetch_radar() ×13×24   시각별 격자 스냅샷을 받는다
      ↓  (동시 6스레드, 재시도 3회)
to_uv()                유향·유속 → u, v 성분 변환
      ↓
snap_to_hours()        24개 슬롯에 가장 가까운 관측을 배정
      ↓
cross_validate()       레이더 격자 3km 안의 부이를 찾아 두 관측을 비교
      ↓
JSON 출력
```

### 주요 함수

| 함수 | 역할 |
|---|---|
| `build_dataset()` | 전체를 묶는 진입점. dict를 반환하므로 서버 전송에 그대로 쓴다 |
| `probe_base_hour()` | 기준 시각 결정 |
| `fetch_buoy` / `fetch_radar` | API 호출 + 정규화 |
| `snap_to_hours()` | 시간축 정렬 (병합의 핵심) |
| `cross_validate()` | 두 자료 교차 검증 |
| `to_geojson()` | 지도용 변환 |

## 설계상 알아둘 점

### 1. 요청에 주기·간격 값을 넣지 않는다

하루 1회 호출로 하루치를 통째로 받으므로, `twRecent`의 `min`(출력 간격) 파라미터를 쓰지 않는다. 부이는 관측소 고유 해상도 그대로 들어온다.

### 2. 기준 시각을 벽시계로 잡으면 안 된다

**HF-RADAR 발행이 2~3시간 지연된다.** 현재 시각 기준으로 슬롯을 만들면 레이더가 전부 탈락한다. 그래서 레이더를 먼저 탐침해 실제 자료가 있는 시각을 기준으로 삼는다.

### 3. 레이더 유속이 부이보다 2~3배 크다

`cross_validation` 결과에서 확인된 계통 편차다. 겹치는 6쌍 전부 같은 방향으로 나타난다.

| 부이 | 레이더 | 거리 | 부이 | 레이더 | 방향차 |
|---|---|---|---|---|---|
| TW_0086 | HF_0040 | 0.11km | 4.9 | 10.5 | +9.3° |
| TW_0076 | HF_0069 | 0.25km | 8.2 | 18.9 | −9.2° |
| TW_0072 | HF_0076 | 1.14km | 7.0 | 13.9 | −2.6° |
| HB_0003 | HF_0063 | 2.48km | 32.8 | 89.2 | +1.1° |

관측 깊이 차이(레이더=표층 수십cm, 부이=수중)와 공간 평균 대 점 관측의 차이로 보인다. **두 값을 같은 유속으로 취급하면 안 되고 보정 계수가 필요하다.**

반면 **방향은 잘 맞는다.** 두 API가 같은 유향 정의를 쓴다는 뜻이다.

### 4. `crdir` 방향 정의가 미검증 상태다

`crdir`이 "흘러가는 방향"인지 "흘러오는 방향"인지 원문에 명시되어 있지 않다. 현재는 **흘러가는 방향으로 가정**해 `u_ms`/`v_ms`를 계산하며, `meta.warnings`에 경고를 싣는다.

이 가정이 틀리면 모든 벡터가 180° 반대가 되므로 궤적 예측이 정반대로 나온다. 검증 후 `DIR_CONVENTION_VERIFIED = True`로 바꾸면 경고가 사라진다.

## 실행 실적 (2026-08-22 기준)

| 항목 | 값 |
|---|---|
| 호출 수 | 부이 76 + 레이더 312 = 약 390회 (한도 10,000의 4%) |
| 소요 시간 | 약 2분 |
| 통합 관측 | 39,476건 (부이 812 / 레이더 38,664) |
| 부이 시계열 | 26,404건 |
| 파일 크기 | 16.7MB (`--compact`) |

용량이 부담되면 `--no-series`로 부이 원해상도 시계열을 빼거나, `--hours`로 범위를 줄인다. 서버 전송 시에는 gzip 압축을 권한다.
